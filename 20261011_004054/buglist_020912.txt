[MEDIUM] (NEW REGRESSION) Forcing floors 2-6 to exactly 2 scribe-alcoves and reserving the
  first as the key room leaves only ONE encounter alcove per floor, so any floor that
  declares more than one hazard/puzzle loses the extra. On the shipped roster this drops
  `dark-leap` entirely: it is never instantiated on any floor or seed.
Location: index.html:638 (`var nP = (depth===1) ? 0 : 2;`)
          index.html:664-666 (keyRoom = alcoveSlugs[0] on floors 2-6)
          index.html:692-694 (only non-key alcoves consume `alcoveIdx`, and with a single
            such alcove `pl[alcoveIdx % pl.length]` only ever evaluates `pl[0]`)
          Roster: world_template.json:180 (`dark-leap`, kind `puzzle`, floor 5), which sits
            AFTER `cursed-ward` (world_template.json:178) in roster order.
          Declared intent: gdd.md:80 (floor-5 puzzle = `dark-leap`), gdd.md:103,
            world_template.txt:104 & 107 ("dark-leap ... shares floor 5 as a secondary
            encounter").
Explanation: `puzzleListAt(5)` returns `[cursed-ward, dark-leap]`, but floors 2-6 now place
  exactly two alcoves and permanently exclude `alcoveSlugs[0]` (the key room) from
  encounters (index.html:693). With one remaining alcove, `alcoveIdx` is 0 once, so only
  `pl[0]` = `cursed-ward` is ever assigned; `dark-leap` is unreachable on every floor.
  Verified by booting the exact file and scanning random/per-floor state: across 30 seeds
  the CURRENT build instantiates floor-5 encounters `{cursed-ward, shades}` only, while the
  pre-change backup (index.html.cycle3.bak:636, whose encounter loop at :683 gave EVERY
  alcove a puzzle) instantiates `{cursed-ward, dark-leap, shades}`. This is a true
  regression of the behaviour the cycle-3 review previously cited as proof-of-fix
  ("f5 cursed-ward + dark-leap — all five named hazards selectable", buglist_011655.txt:115-116).
  The Phase-2 checks do NOT catch it: `dark-leap` is absent from `required_encounters`
  (world_template.json:67-71) and `window.systemState()` echoes the whole roster id list
  regardless of placement (index.html:2198), so the systemic check stays green while the
  content is missing. Mechanically the game still plays; a declared hazard/encounter class
  and its GDD-described recon puzzle are simply gone.
Fix approach (choose one, minimal):
  (a) lift the key-room exclusion to hazards only — a `kind:"puzzle"` encounter (dark-leap)
      may share the key room since it is not a "hazard" and `checkPlacement` already excludes
      `kind:"puzzle"` (scripts/check_template.mjs:96); assign leftover `pl[1..]` to the
      key-room alcove; or
  (b) place the secondary floor-5 puzzle in a `shadow-hall`/corridor, or add a third alcove
      on floors whose roster declares >1 puzzle/hazard; or
  (c) if the single-encounter-per-floor model is intended, remove `dark-leap` from
      `encounter_roster` and its GDD/world_template.txt references so the declared content
      matches what ships.
  Re-run the per-floor scan afterwards (expect `dark-leap` to appear on floor 5).

[MEDIUM] (CARRIED — deliberately deferred in cycle 3; NOT addressed by this change) Hazards
  are still placed in a `role:"puzzle"` room. TORRE §6.4.4 and §14 require a hazard's room
  to carry archetype `role:"hazard"`; the only such archetype (`shadow-hall`) holds
  creatures, while every hazard sits in a `scribe-alcove` (`role:"puzzle"`).
Location: index.html:692-694 (hazards assigned to non-key `scribe-alcove`s);
          index.html:298-318 (archetypes: `shadow-hall.role:"hazard"`,
            `scribe-alcove.role:"puzzle"`, mirrored in the embedded block);
          TORRE_NOSFERATU.md:216-217 (§6.4.4) and TORRE_NOSFERATU.md:492-493 (§14).
Explanation: The change reworded §6.4.1 (line 184-189) and §15 (line 504-505) from
  "never on a cut-edge" to "never required for progress" — and the implementation now
  satisfies that rewording (the key room is encounter-free; verified below). But §6.4.4
  and §14 still assert the hazard's ROOM archetype carries `role:"hazard"`, and the shipped
  engine does not. The change therefore left the spec internally contradictory: §6.4.1/§15
  are now met while §6.4.4/§14 are not. Data-model / spec-conformance only; no gameplay or
  Phase-2 impact (spatial gate passes on all floors).
Fix approach: either (i) author a dedicated `role:"hazard"` archetype and route hazards
  there (the cycle-2/3 deferred restructure), or (ii) amend §6.4.4 and §14 to state the
  hazard shares the puzzle-room archetype and is identified by its `kind:"hazard"` roster
  entry. Whichever is chosen, make the two clauses agree with §6.4.1.

  `tryRelight` returns false without feedback. No misleading toast is shown (the handler at
  :1827 ignores the return), so this is minor UX only.

  `canRelight` once and reuse it in `openJournal`).

[LOW] Snuff-caused guttering cannot be ended by wax even after the flame is re-lit: a match
  during guttering sets `G.snuffed=false` but `G.gutterCause` stays `'snuff'`, so a later
  wax-cake never clears it (the candle is lit and fuelled, yet still gutters to death).
Location: index.html:1653-1655 (`tryRelight` guttering branch clears `snuffed`, +1 grace,
            leaves `guttering`/`gutterCause` unchanged) and index.html:1329 (wax-cake clears
            guttering only when `G.gutterCause==='wax'`).
Explanation: The cause-qualified wax-cake rule is the intended new behaviour and it does make
  the code consistent with gdd.md:155 ("a snuff with no match is not recoverable") + :156.
  The edge is the state `snuffed=false, guttering=true (cause 'snuff'), wax>0`, in which the
  flame is described as "lit" yet remains terminal. Wording in TORRE §8 ("you may still reach
  a match or the exit") and gdd.md:156 ("only wax ... ends it") does not spell out the
  cause qualifier, so a reader could expect the wax-cake to catch the flame.
Fix approach: documentation-only, or (optionally) clear guttering when `wax>0 &&
!snuffed`; at minimum add the cause qualifier to gdd.md:156 and TORRE §8.

[LOW] Defensive: the keyRoom fallback can, on a hypothetical degenerate floor with neither a
