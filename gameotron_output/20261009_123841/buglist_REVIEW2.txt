NEW / REMAINING ISSUES

[MEDIUM] BACK from a Pause submenu unpauses the music while still on the PAUSE screen
  Location: index.html:776-777 (goBack), index.html:1259-1260 (pause action), index.html:1574-1575 (drawPads irrelevant)
  Explanation: Opening HOW TO PLAY or SETTINGS from the Pause menu keeps Audio.paused = true (correct). But the
  BACK button calls goBack(), whose PAUSE branch unconditionally invokes Audio.setPaused(false) and then
  showScreen('PAUSE'). The game is still paused, yet the music bus ramps back to full volume and the bed plays
  behind the paused playfield. GDD §7 requires Pause to "freeze the game clock, token timers, and audio music
  bed". Only RESUME should un-pause audio, and RESUME itself already calls Audio.setPaused(false) (:1263).
  Fix approach: Remove the Audio.setPaused(false) calls from goBack(); re-assert Audio.setPaused(true) when
  returning to PAUSE, so audio state is owned by the pause/resume actions only.

[MEDIUM] Combo x8 milestone (+150) is awarded on every correct route while the combo sits at x8
  Location: index.html:991 (cap), index.html:1028-1031 (milestone)
  Explanation: correctRoute() caps the combo with `G.combo = Math.min(8, G.combo + 1)`, so once the combo
  reaches 8 it remains 8. The milestone check `if (G.combo === 8) { addScore(150); ... }` therefore fires on
  the completing route AND on every subsequent correct route for as long as the chain survives, producing an
  unbounded score faucet. GDD §4.3 defines this as a one-time "Combo chain completion (combo reaches x8) +150".
  Fix approach: Track a boolean (e.g. G.combo8Awarded) reset when the combo resets, and grant the +150 only on
  the transition 7 -> 8.

[MEDIUM] Transient input state (charging / grabbed / pointerActive) is not cleared on pause, so resuming after
         a mid-gesture auto-pause can fire a phantom roll or swallow the first input
  Location: index.html:1100-1118 (pointerActive), index.html:1138-1141 (charging), index.html:1258-1263
            (pause/resume), index.html:1304-1311 (visibilitychange auto-pause)
  Explanation: `pause` sets G.pauseStart and shows the Pause screen but leaves G.charging/G.grabbed and the
  module-level pointerActive flag as they were. When the game auto-pauses on visibilitychange while the player
  is holding to charge (:1305-1306), the release that happens while hidden is either not delivered or arrives
  with G.state already 'PAUSE' (handleUp only dispatches gUp when state === 'GAMEPLAY', :1118). On return and
  RESUME, G.charging is still true with no live pointer, so the next pointerup that is not a token grab calls
  doRoll() (:1170-1173) at an unintended charge tier. Likewise pointerActive can remain true across the pause,
  so the first genuine touchstart after resume is discarded by the `if (pointerActive) return;` guard (:1178)
  before that release triggers the phantom roll. Fix approach: On entering PAUSE, clear G.charging=false,
  G.charge=0, G.grabbed=null, pointerActive=false, activeTouchId=null (and release any dragged token back to
  snapBack), so no gesture state survives a pause.

[LOW] Title "demo roll" sound plays twice for a single canvas tap
  Location: index.html:1104-1107 (handleDown), index.html:1294-1295 (document pointerdown delegate)
  Explanation: A tap on the decorative title canvas fires the canvas pointer handler (handleDown → title_demo_roll)
  AND the document-level pointerdown delegate's fallback (title_demo_roll), retriggering the same SFX twice on
  both touch and mouse. Buttons are unaffected (the delegate returns early for data-action).
  Fix approach: Guard the demo roll so it is triggered in only one place (e.g. drop the fallback in the
  document delegate and let handleDown own it, or vice-versa).

[LOW] Junk Near-Miss window is 0.4 s but GDD §4.4 specifies 0.3 s for edge discard
  Location: index.html:944-945 (nmwJ = 0.4 + blueprints ? 0.4 : 0)
  Explanation: The spec gives a distinct "final 0.3 s" window for flick-discarding Junk, while correct/enemy
  routes use 0.4 s. The junk branch reuses the 0.4 s constant, making junk near-misses easier than documented
  and inconsistent with the other triggers.
  Fix approach: Use a dedicated 0.3 s base for the junk branch (still widened by the Blueprints module).

[LOW] Zone 1 "one token at a time" is not enforced
  Location: index.html:870-907 (doRoll), index.html:909-925 (spawnToken)
  Explanation: gDown() only grabs a token when the press is within grabR (~64 px); a token that has snapped
  back sits ~buttonR*1.25 px above the button centre, just outside a 64 px grab radius. Tapping the button
  centre therefore starts a second charge and a second token while the first is still alive, contradicting
  GDD §2.3/§4.4 ("One token at a time" in Zone 1). With account blueprints the grab radius grows and the
  behaviour flips, which is inconsistent.
  Fix approach: In doRoll(), ignore/queue the roll if G.tokens.length > 0 while G.zone === 1 (or while
  !G.endless and zone 1).

[LOW] Endless mode restarts at Zone 1 instead of continuing the ramp
  Location: index.html:1251-1252 (endless action), index.html:804-821 (startRun)
  Explanation: "PLAY ENDLESS MODE" calls startRun(true), which resets G.zone = 1. GDD §4.3 describes endless as
  "zones continue with capped linear ramp", not a fresh Zone 1. The flag only disables the victory check.
  Fix approach: Accept a starting zone for endless (e.g. startRun(true, 6)) or keep zone 5's difficulty as the
  endless baseline.

[LOW] High-contrast accessibility toggle still absent
  Location: index.html:210-228 (Settings), index.html:360/1277 (settings object)
  Explanation: GDD §5 and §8 (Screen 5) require a "Reduced-flash / high-contrast toggle". Only Reduced Flash
  exists; there is no high-contrast mode, so the accessibility requirement is only half met.
  Fix approach: Add a persisted highContrast setting and apply a high-contrast CSS class/outline treatment.

[LOW] Local `var Audio` shadows the built-in window.Audio constructor
  Location: index.html:379
  Explanation: The IIFE declares an object named Audio while using window.AudioContext (aliased to AC). It works
  because AudioContext is aliased, but the shadowing is fragile for future edits and confuses tooling.
  Fix approach: Rename the local object (Sound/Sfx) and update its ~40 references, or rename the context alias.

[LOW] Extensive magic numbers with no named constants
  Location: index.html:713 (300 particle cap), 726 (100 confetti cap), 871-872 (tier seconds), 997-998/1000
            (score values), 1008/944 (near-miss windows), 1034 (shake), etc.
  Explanation: Balance values, caps and tuning constants remain inlined throughout, making later tuning
  error-prone and obscuring intent (GDD §10.2 warns about pooled caps/balancing).
  Fix approach: Hoist tuning constants into a CONFIG block (PARTICLE_CAP, CONFETTI_CAP, SCORE_*, TIER_SECONDS,
  NEAR_MISS_WINDOW, ...).

[LOW] Dead resume branch on the pause button
  Location: index.html:767-768 (pauseBtn display), index.html:1298-1302 (pauseBtn handler)
  Explanation: pauseBtn.style.display is 'block' only when G.state === 'GAMEPLAY', so the `else if
  (G.state === 'PAUSE') performAction('resume')` branch can never be reached while the button is hidden.
  Fix approach: Remove the dead branch (resume is handled by the Pause menu RESUME button), or show the button
  in PAUSE if the toggle behaviour is intended.

[LOW] chainPending is not reset when a zone advances
  Location: index.html:1069-1082 (advanceZone), index.html:1356-1365 (update spawn)
  Explanation: advanceZone() resets G.zoneRolls but leaves G.chainPending untouched, so a chain queued at the
  end of one zone can spawn ~0.45 s into the next zone. startRun() clears it, but the per-zone transition
  does not.
  Fix approach: Set G.chainPending = 0 in advanceZone().

[LOW] Active tokens are not repositioned on resize / orientationchange
  Location: index.html:641-659 (resize), index.html:908-925 (spawnToken target coords)
  Explanation: resize() recomputes button/pad/token anchors, but tokens already on screen keep their absolute
  x/y/tx/ty, so after an orientation change a token can be left misplaced relative to the button/pads and the
  SOCKET target.
  Fix approach: On resize, recompute each token's target (tx/ty) and clamp it into the new viewport, or pause
  and re-place tokens.

[LOW] RESET DATA confirm lock is a fixed 400 ms wall-clock window
  Location: index.html:1231-1246 (askConfirm / confirmLockUntil)
  Explanation: The auto-accept guard compares performance.now() against a 400 ms deadline. A slow release
  (long-press on RESET DATA longer than 400 ms) lets the synthesised compatibility click land after the lock
  expires; if the YES button happens to sit under the finger, the confirm can still accept itself. The fix
  should be gesture-based rather than time-based.
  Fix approach: Arm the YES/CANCEL handlers only on the first pointerdown that occurs after the overlay is
  shown (e.g. ignore clicks until a fresh pointerdown/pointerup pair lands inside the overlay).

[LOW] No-op statement in snapBack()
  Location: index.html:983
  Explanation: `tk.x = tk.x; // keep` is a no-op self-assignment with a comment; harmless but misleading.
  Fix approach: Delete the line (and the stale comment).

[LOW] Token grab radius grows very large on desktop, inconsistent across devices
  Location: index.html:920 (grabR = max(64, tokenR*1.9) * (1+grabBonus)), index.html:1151 (acquireR tokenR*2.6)
  Explanation: On a 1080-tall desktop tokenR ≈ 73, so grabR ≈ 139 px and acquireR ≈ 190 px, versus ~64 px on a
  375-wide phone. Acquisition feel is dramatically device-dependent (prior LOW was only partially addressed by
  the max(64, ...) floor, which does nothing on large screens). GDD §3.2 specifies "~64 px radius".
  Fix approach: Clamp the upper bound (e.g. clamp(tokenR*1.9, 64, 96)) or use a fixed CSS-px acquisition radius.

[LOW] SOCKET pad can overlap the HUD on very short landscape viewports
  Location: index.html:654 (zonesPos.socket = buttonY - buttonR*2.35), index.html:19-22 (HUD)
  Explanation: On a very short landscape window (e.g. 800x400) the SOCKET pad top edge (~47 px) rises into the
  fixed HUD/stability bar area, partially occluding the pad label/border.
  Fix approach: Derive the SOCKET y from max(HUD height + padHalf, buttonY - buttonR*2.35) or hide the HUD
  STABILITY element when space is tight.
