FAILED INTERACTION MECHANICS
------------------------------------------------------------------------
[131121] [HIGH] [375x667 only] RESET DATA confirmation is auto-accepted by the
        same touch that opens it.

        Observed (mobile touch, real touch context, hasTouch=true):
          • Tap RESET DATA  -> confirm overlay appears
          • ~same instant     the browser-synthesised `click` from that same
                              tap is re-hit-tested at the same coordinates and
                              lands on the newly-shown YES button
          • overlay closes and the reset callback RUNS without user consent.

        Captured event trace (tap on RESET DATA, element at 187.5,339):
          pointerdown:BUTTON:resetdata:touch
          touchstart:BUTTON:resetdata
          click:BUTTON:confirmYes:touch      <-- trailing click hits YES
          └ overlay.classList.contains('active') === false afterwards

        Contrast: selecting the button programmatically (dispatch a single
        PointerEvent) leaves the overlay open correctly, and the same flow on
        desktop mouse (1920x1080, 800x600) leaves the overlay open and waits
        for a choice. Because the RESET DATA button centre and the YES button
        centre overlap at 375px width, touch users reset all saved data with no
        confirm opportunity.

        Root cause: actions are dispatched from a `pointerdown` listener
        (index.html line 1216-1226 / performAction 'resetdata' -> askConfirm,
        line 1200-1211). `e.preventDefault()` on pointerdown does NOT suppress
        the compatibility `click` that follows touchend, so the click is
        delivered to whatever element now occupies the touch coordinates — the
        confirm dialog's YES button. This is standard browser touch->click
        behaviour (iOS/Android/desktop-touch), not a Playwright artefact.

        Impact: destructive "Reset all saved data" executes without confirmation
        on touch devices. Classification HIGH (data loss, broken confirm UX).
        Not observed on desktop viewports because the two button centres do not
        overlap there.

        Testing workaround used: the mobile suite treated this tap as a detected
        failure (test resetdata_shows_confirm = FAIL) but continued; all other
        mobile checks passed.
